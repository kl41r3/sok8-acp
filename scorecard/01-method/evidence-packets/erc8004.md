# ERC-8004 (Trustless Agents) — evidence packet

Home layer: L1 (also L2). Origin: hybrid (`spec-erc8004`). Status on EIP site: Draft.

## Canonical locators

- `spec-erc8004` https://eips.ethereum.org/EIPS/eip-8004
- Magicians thread https://ethereum-magicians.org/t/erc-8004-trustless-agents/25098
- Authors include MetaMask, Ethereum Foundation, Google, Coinbase (citation block on the EIP)
- Corpus companions: `oa-w7164615253` operational readiness of ERC-8004; `oa-w7166252676` “Can Trustless Agents Be Trusted?”

## Documented artifacts

- Three registries, deployable as per-chain singletons on L2 or mainnet:
  - Identity: ERC-721 + URIStorage; `agentRegistry` = `{namespace}:{chainId}:{identityRegistry}`; registration file with A2A / MCP / ENS / DID / wallet endpoints; optional `x402Support`.
  - Reputation: `giveFeedback` / revoke / appendResponse; on-chain value + optional IPFS file; `getSummary` requires clientAddresses filter because unfiltered results are Sybil-prone.
  - Validation: request/response hooks for stakers, zkML, TEE oracles, trusted judges; response 0–100.
- Payments explicitly orthogonal. Feedback MAY include `proofOfPayment` (x402 tx hash).
- Security Considerations: Sybil attacks possible; on-chain pointers cannot be deleted; “cannot cryptographically guarantee that advertised capabilities are functional and non-malicious.”
- `supportedTrust` optional; if absent, used only for discovery, not trust.

## Failures named in sources

- Ledger L1: identity ≠ capability or honest execution (T1).
- EIP: reputation inflation; capability claims not cryptographically guaranteed.
- Feedback scores do not bind AP2 mandate terms or x402 settlement conditions (Result 2 interoperability claim in the original instrument; consistent with T1).
- Draft ERC, not final. Cross-chain: an agent on chain A can operate elsewhere, but reputation is per-registry unless aggregators exist. CS1 metric (cross-chain consistency) is not specified in the EIP.
- Validation incentives/slashing are out of scope of the registry.
